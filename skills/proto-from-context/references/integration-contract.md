# Proto From Context — BSA Integration Contract

Self-describing integration surface for the `proto-from-context` exporter. Third and final Stage 6 contract exporter in the v1.3.x line, completing the trio (OpenAPI / AsyncAPI / proto). Status: experimental — the v1.3.2 ship is a skeleton that scaffolds the bundle shape so v1.3.2.x / v1.3.3+ can iterate against a stable contract.

## Status + Ownership

- **Skill role:** operator-driven exporter. NOT a sidecar — see SKILL.md §"Why an exporter, not a sidecar". NOT registered in `config/sidecar_registry.yaml`.
- **Output ownership:** generated artifacts live under `<output_dir>/` (default `analysis/handoff/contracts/proto/`) and are **operator-shipped deliverables**. They never enter `analysis/canonical/` (INV-02 stays intact). The exporter writes only inside `output_dir`.
- **Validation binding:** opt-in; does NOT contribute to a mandatory marker. Operators choosing to enforce proto3 conformance run `protoc` themselves against the emitted `.proto`.

## Inputs

Required:
- `analysis/canonical/stage6/A61_anchor_map.csv` — the post-audit, orchestrator-promoted anchor map. Source of every materialized proto rpc + the surrounding service grouping.

Optional:
- `analysis/canonical/stage6/interface_contract_model.md` — descriptive prose. v1.3.2 does NOT parse it.
- `analysis/canonical/stage6/boundary_input_output_map.md` — same: documented as future input, not consumed in v1.3.2.

Out of scope:
- `analysis/proposals/stage6/*` — pre-promotion proposals. Only canonical (post-audit) anchors are consumed.

## Outputs

Two files per run, both inside `output_dir`:

### `services.proto`

Minimal-valid proto3 file. Top-level shape:

```proto
syntax = "proto3";

package bsa.contracts;

// Generated by skills/proto-from-context (v1.3.2 skeleton).
// Operator must enrich each rpc with real Request/Response message
// fields and choose unary vs streaming semantics before shipping.

service Orders {
  // bsa-anchor: <ClaimID-or-A51Ref>
  rpc Created(OrdersCreatedRequest) returns (OrdersCreatedResponse);
}

message OrdersCreatedRequest {
  // Placeholder field — operator must enrich with real proto3 type
  // and rename for clarity (extracted from `{order_id}` template in
  // ElementID `/orders/{order_id}/created`).
  string order_id = 1;
}

message OrdersCreatedResponse {
  // Placeholder — operator enriches with real response fields.
}
```

For each A61 anchor with `AnchorClass=contract` AND a path-shaped `ElementID` AND a successful proto-identifier synthesis from the path, one rpc is emitted (grouped under the synthesized service block). Anchors that don't pass these gates go into `anchor_manifest.json::unmapped_anchors` with a structured reason.

**Path-shape regex is identical to v1.3.0 OpenAPI exporter's path-shape regex (post-R2 form):** `^/[A-Za-z0-9_/{}.~-]*$`. Same `%`-rejection rationale (atomic regex-level reject closes the recursive-decode attack surface; encoded traversal at any depth surfaces as `element_id_not_path_shaped`). Same balanced-brace template scan, but **with a tightened parameter-name charset for v1.3.2** — the proto3 field-name grammar `^[A-Za-z_][A-Za-z0-9_]*$`, NOT the v1.3.1 AsyncAPI `^[A-Za-z0-9_-]+$` (which allowed hyphens). v1.3.2 R1 lesson: when a gate's accepted-token charset binds a downstream emission, the gate MUST match the downstream consumer's grammar — not a sibling exporter's grammar. AsyncAPI/OpenAPI accept hyphens in parameter names (`{order-id}`); proto3 does not (proto3 field names cannot contain `-`). v1.3.2 therefore rejects `{order-id}` (hyphen), `{9id}` (leading digit), `{tenant.id}` (dot), `{user id}` (space), `{order/sub}` (slash) at gate time as `element_id_not_path_shaped`.

**Proto-identifier synthesis pass** (NEW for v1.3.2 — the only gate added beyond v1.3.0/v1.3.1):
1. Strip leading `/` from ElementID.
2. Split on `/` into segments.
3. Filter out template segments (`{order_id}`).
4. If no non-template segments remain → `proto_identifier_synthesis_failed` (e.g., `/{a}/{b}` or root `/`).
5. First non-template segment → service name candidate (PascalCase via segment-to-PascalCase: split on non-alphanum, capitalize each word, concat).
6. Remaining non-template segments → method name candidate (PascalCase concat). If empty, defaults to `Invoke`.
7. Both service and method names MUST match proto3 identifier regex `^[A-Za-z_][A-Za-z0-9_]*$`. If either fails (e.g., segment starts with a digit like `/123abc/foo` → `123abc` PascalCases to `123abc` which starts with digit → fail), surface as `proto_identifier_synthesis_failed`.

**Service deduplication:** multiple anchors mapping to the same service name share a single `service { ... }` block — rpcs are appended in input order. Cross-anchor `<Service>.<Method>` collisions are rejected (first wins; rest surface as `duplicate_rpc_collision`).

**Message naming:** request/response messages use `<Service><Method>Request` / `<Service><Method>Response` to avoid cross-service collisions in the single-file output. Operators with single-service projects can rename to flat form (`CreatedRequest`) post-export.

**Field-tag numbering:** template parameters (`{order_id}`) become `string <name> = <N>;` fields in the request message, with `<N>` numbered sequentially starting at 1 within each message (proto3 tag numbers must be in [1, 536870911]; the skeleton stays well below the reserved range 19000-19999).

Default rpc form is **unary** (`rpc M(Req) returns (Resp);`); operator changes to streaming (`stream Req` / `stream Resp`) post-export. The skeleton can't infer streaming intent from the A61 anchor alone.

### `anchor_manifest.json`

Conforms to `skills/proto-from-context/references/anchor_manifest.schema.json` (Draft 2020-12, extends `governance/schemas/sidecar_anchor_manifest.base.schema.json`).

Top-level: `manifest_version`, `generated_at`, `sidecar` (literal `"proto-from-context"`), `canon_policy_version`, `view_files`.

Per `view_files[]` entry:
- `path` — repo-relative or absolute path to the emitted `services.proto` (matches `\.proto$`).
- `format` — literal `"proto3"` (discriminator for future spec-version drift; proto2 is intentionally NOT supported).
- `anchor_map` — array of `{view_element_id, view_element_kind, a61_anchor_id, notes?}`.
- `unmapped_anchors` — array of A61 anchor IDs that were skipped (with structured reasons).

`view_element_kind` enum: `Service` / `Rpc` / `Message` / `Enum`. v1.3.2 emits Service + Rpc only; Message + Enum reserved for future structured-input releases.

`view_element_id` convention:
- `Service`: the service name (e.g., `Orders`). One Service entry per distinct synthesized service across all anchors (deduplicated).
- `Rpc`: `<Service>.<Method>` (e.g., `Orders.Created`). One Rpc entry per materialized anchor.

## Validation rules

Per emitted `services.proto`:
1. **Syntax declaration** — first non-comment statement MUST be `syntax = "proto3";` (per the proto3 spec — required to be the first non-comment line of the file).
2. **Package declaration** — `package <name>;` is always emitted by this exporter (default `bsa.contracts`; configurable via `--package`). Note: the proto3 spec allows `package` to be omitted, but this exporter always writes one for downstream-tooling friendliness.
3. **No-crash invariant** — even with zero contract-class anchors, the exporter emits a valid `services.proto` with the syntax + package declarations and no service/message blocks; the manifest has empty `anchor_map`.

Per emitted `anchor_manifest.json`:
1. **Schema conformance** — validates against `references/anchor_manifest.schema.json` (Draft 2020-12).
2. **Service deduplication** — every distinct synthesized service produces exactly one `Service` entry in `anchor_map`, regardless of how many rpcs it contains. The same anchor may produce 1 Service + 1 Rpc entry (when its service is first-seen) or 1 Rpc entry only (when its service was already added by a prior anchor).
3. **Rpc/service consistency** — every Rpc entry's `view_element_id` (`<Service>.<Method>`) has a matching Service entry with `view_element_id == <Service>`. Held by construction.
4. **No orphans in proto** — every `service` block + `rpc` line in `services.proto` MUST have a matching `anchor_map` entry. Held by construction.

## Gate behavior

**Non-blocking by default in v1.3.2.** The exporter:
- Always emits both files; an empty A61 input produces an empty-but-valid skeleton (syntax + package declarations only).
- Never modifies `analysis/canonical/`.
- Never invokes git.
- Never invokes `protoc`.
- Never edits source files referenced by Stage 6 artifacts.

## CLI

```
python3 skills/proto-from-context/scripts/generate_proto.py --workspace <path>
python3 skills/proto-from-context/scripts/generate_proto.py --workspace <path> --input <a61_csv>
python3 skills/proto-from-context/scripts/generate_proto.py --workspace <path> --output-dir <dir>
python3 skills/proto-from-context/scripts/generate_proto.py --workspace <path> --package my.events
python3 skills/proto-from-context/scripts/generate_proto.py --workspace <path> --print-only
python3 skills/proto-from-context/scripts/generate_proto.py --workspace <path> --quiet
```

`--input` overrides the canonical A61 path AND bypasses the `analysis/`-init guard, mirroring v1.2.18 miner's `--telemetry-dir` semantic + v1.3.0/v1.3.1 R1-FIX-1. `--output-dir` overrides where the two files go: implicit-missing path is permissive (created on demand), explicit-missing path is rejected (operator typo defense, mirrors v1.2.19 patcher R1-FIX-1). Outside-workspace `--output-dir` records absolute path in manifest (mirrors v1.2.19 patcher R1-FIX-2). `--package` populates the `package <name>;` declaration in the proto file (default `bsa.contracts`); MUST match proto3 package-name syntax `^[A-Za-z_][A-Za-z0-9_]*(\.[A-Za-z_][A-Za-z0-9_]*)*$`.

## Failure modes summary

| Failure | Behavior |
|---|---|
| Missing canonical `A61_anchor_map.csv` (and `--input` not given) | Exit 2, message "Stage 6 not promoted" |
| Malformed A61 CSV (parse / missing required columns) | Exit 2, structured error |
| `ElementID` containing literal `..` | Rejected by `_TRAVERSAL_HINT` regex; recorded in `unmapped_anchors` with reason `element_id_path_traversal` |
| `ElementID` containing percent-encoding (any depth: `%2e`, `%252e`, `%25252e`, etc.) | Rejected by the path-shape regex (`%` is not in the character class); recorded with reason `element_id_not_path_shaped`. Same R2 design as v1.3.0/v1.3.1: atomic regex-level reject |
| `ElementID` with malformed OpenAPI-style template (`/users/{id`, `/users/{}`, `/users/}{`, `/users/{{id}}`) | Rejected by the brace-balance scan; recorded with reason `element_id_not_path_shaped` |
| `ElementID` with template whose name doesn't match the proto3 field-name grammar `^[A-Za-z_][A-Za-z0-9_]*$` (`{order-id}` hyphen, `{9id}` leading digit, `{tenant.id}` dot, `{user id}` space, `{order/sub}` slash) | Rejected by the brace-balance scan's parameter-name charset check (v1.3.2 R1 lesson — tightened from v1.3.1's `^[A-Za-z0-9_-]+$` to match the actual downstream consumer grammar); recorded with reason `element_id_not_path_shaped` |
| `ElementID` in dot-style (`OrderService.CreateOrder`, `orders.created`) | Rejected by the path-shape regex (no leading `/`); recorded with reason `element_id_not_path_shaped`. v1.3.2 only supports path-style — see SKILL "Out of scope" |
| Anchor with non-path-shaped `ElementID` | Rejected; recorded in `unmapped_anchors` |
| `ElementID` with all template segments (`/{a}/{b}`) or root (`/`) | Rejected by proto-identifier synthesis (no non-template segment for service name); recorded with reason `proto_identifier_synthesis_failed` |
| `ElementID` first segment doesn't yield valid proto identifier (`/123abc/foo`) | Rejected by proto-identifier synthesis (PascalCased name doesn't match `^[A-Za-z_][A-Za-z0-9_]*$`); recorded with reason `proto_identifier_synthesis_failed` |
| Two anchors map to the same `<Service>.<Method>` | First wins, rest skipped with reason `duplicate_rpc_collision` |
| Output dir explicit + missing | Exit 2 (mirrors v1.2.19 patcher R1-FIX-1 + v1.3.0/v1.3.1 exporters) |
| Output dir implicit + missing | Permissive: created on demand |
| Bad AnchorID (fails `^ANC-[A-Z0-9_-]+$`) | Silently dropped (would fail manifest schema if surfaced; mirrors v1.3.0/v1.3.1 exporter approach) |
| `--package` doesn't match `^[A-Za-z_][A-Za-z0-9_]*(\.[A-Za-z_][A-Za-z0-9_]*)*$` | Exit 2, structured error (operator typo defense) |
